## 1. Goal

Explain Prism — what it is, how it works, and what every part does — to someone who has never seen
the codebase, in plain language.

Two deliverables from one source, per owner decision 2026-08-05:

1. **`/docs`** — plain Markdown, readable directly in an editor or on GitHub with no build step
2. **A VitePress site** — the same content with navigation, search and a rendered architecture view

The Markdown is the source of truth. The site renders it. There is no second copy to drift.

## 2. Current state

`apps/docs` is a stub TypeScript package: `src/index.ts`, `src/index.test.ts`, a `moon.yml` and two
Vitest configs. There is no site, no content, no VitePress.

Existing documentation lives in `plans/` and is written for *building* Prism — milestones, ADRs,
architecture specs, verification procedure. It is dense, internally cross-referenced and assumes the
reader is implementing the next milestone. It is the wrong register for someone trying to understand
the product. This milestone does not replace it; `plans/` stays as the engineering record and `/docs`
becomes the explanation.

## 3. Audience and register

Three readers, in priority order.

| Reader | Wants | Gets |
|---|---|---|
| **Someone evaluating Prism** | What is this, is it for me, what does it cost me | Introduction, concepts, quickstart |
| **Someone using it** | How do I do the thing I want | Guides per surface, feature reference |
| **Someone changing the code** | Where does this live, why is it like this | Architecture, package reference, contributing |

Register rules, since "easy to understand" is the explicit requirement:

- Short sentences. One idea each.
- Define a term the first time it appears. "Blast radius" means nothing to a new reader.
- Concrete before abstract: show the output, then explain the mechanism.
- No internal shorthand. Never "M-049" or "ADR-0027" in body text without saying what it is.
- Every concept page opens with a one-sentence answer to "what is this and why do I care".
- Diagrams where structure matters — Mermaid, rendered by VitePress, readable as text on GitHub.

## 5. Scope — phases

| Phase | Work |
|---|---|
| 1 | `/docs` structure, navigation manifest, writing-style guide, glossary skeleton |
| 2 | Concepts and architecture — the hard writing, and the part with the most value |
| 3 | Surface guides and feature pages, written against the shipped behaviour and verified by running it |
| 4 | Generated reference: Core API, CLI commands and MCP tools generated from source so they cannot drift |
| 5 | VitePress site over `/docs`: theme aligned to [ADR-0014](../adr/0014-uxpilot-dark-product-ui.md) dark tokens, local search, Mermaid, `docs:dev` / `docs:build` tasks |
| 6 | Link check, terminology sweep, read-through as a first-time reader |

## 6. Out of scope

- Marketing site, landing page, blog
- Video or animated walkthroughs
- Translations
- Hosting and deployment — build locally; publishing is M-039 or later
- Rewriting `plans/` — different audience, stays as-is
- API docs generated by TypeDoc — hand-written reference reads better and this surface is small enough

### What the checks caught

Worth recording, because it is the argument for having written them. The first
draft of the hand-written pages contained six false claims that read perfectly
plausibly:

| Claim | Reality |
|---|---|
| `prism health --history` | `health` takes no `--history`; history is an extension screen and an MCP tool |
| `prism bundle --in dist/stats.json` | The flag is `--artifact <id>` |
| `prism test-impact <paths…>` | Takes a single `<target>` |
| `prism rename <from> <to>` | `<target> [newName]` |
| Index at `.prism/cache.db` | `.prism/cache/index.sqlite` |
| Health history at `.prism/history/` | In the index cache |

Plus a Core SDK page written against method names that do not exist
(`openWorkspace`, `getRepositoryDna`, `getHealthScore`, `findCycles`, …) — the
real entry point is `Prism.create().openRepository()`.

`check-docs.mjs` now fails on all of the first six categories, and was itself
verified by injecting each error and confirming it fires.

## 9. Risks

| Risk | Mitigation |
|---|---|
| Docs drift from code immediately | Reference sections generated; a CI check fails when generated output differs |
| Written in engineering register despite the requirement | Style guide in Phase 1; explicit terminology sweep in Phase 6 |
| Scope inflation — this could absorb unlimited time | Content plan in §4 is the contract; anything else is a follow-up |
| Two deliverables diverge | Only one source. The site renders `/docs`; it never holds its own copy |
| Site theme drifts from product design | Reuse the ADR-0014 dark tokens directly rather than re-picking colours |
